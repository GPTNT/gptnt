# Documentation reader journeys and component map

- Status: checked Stage 1 planning evidence
- Applies to: GPTNT v2 and later
- Public site status: not published

## Purpose

This map connects each planned page to a reader's starting state, required outcome, prerequisites,
reference anchors, adjacent pages, and failure exits. It also assigns Zensical components where a
component clarifies a choice, state, relationship, or supporting detail.

The map defines the contracts among the three connected authoring slices. It does not prescribe a
component for every section. A page author must still verify every command, field, path, and claim
against v2 before drafting public prose.

## Component notation

| Label     | Zensical feature                        | Use in this map                                                                  |
| --------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| `Adm`     | Admonition                              | A visible requirement, state, caveat, verification, example, or recovery summary |
| `Tabs`    | Linked content tabs                     | Mutually exclusive variants that perform the same task                           |
| `Ann`     | Code annotation                         | A line whose meaning depends on GPTNT rather than the file syntax                |
| `Gloss`   | Tooltip, abbreviation, or glossary link | The first useful mention of a defined project term                               |
| `Diagram` | Mermaid                                 | A relationship, lifecycle, state transition, data flow, or service call sequence |
| `Actions` | Buttons or instant previews             | A primary next action or a useful definition preview                             |
| `Tags`    | Controlled page tags and icons          | Search and lateral discovery outside the navigation branch                       |

Use `Adm` types from the documentation-site specification. Requirements remain visible. Optional
detail may collapse, but required steps and failure recovery must not depend on a collapsed block.

## Journey acceptance checks

### Runner

1. Start on Home and choose installation.
2. Complete platform setup and the applicable doctor checks.
3. Run the quickstart and identify every generated artefact.
4. Open the result without searching source code for a path or command.
5. Follow one failed game or runtime state to a symptom-led correction.
6. Open a deep CLI or runtime reference page and return to the task.
7. Use choose-next-workflow to continue to model integration, statics, results, or submission.

### Model integrator

1. Start from choose-next-workflow and create a player profile.
2. Configure a provider without placing a secret in a tracked example.
3. Select identity and capabilities with links to their effect on comparison.
4. Prepare the required manual profiles and verify the resulting artefacts.
5. Create and validate a manifest, then generate specifications.
6. Run and inspect the model output.
7. Reach the supported Python interfaces when local configuration is insufficient.
8. Follow a provider, response, or manual failure to a distinguishing check and correction.

### Result submitter

1. Identify the required interactive suites and static targets from current instructions.
2. Run or locate each required output and confirm completion.
3. Build and inspect DuckDB without deleting the source Parquet.
4. Build a version-2 bundle with the correct submitter and target data.
5. Validate the bundle and correct one representative schema or completeness failure.
6. Use dry-run where the command supports it.
7. Submit through the current repository workflow.
8. Reach exact suite-lock, result, provenance, bundle, and CLI reference from the procedure.

### Contributor

1. Start at the runtime concept and select a subsystem by operation.
2. Trace the subsystem to selected generated objects, channels, states, or payloads.
3. See the implementation-scope statement before interpreting an object as an extension point.
4. Follow the data or call path back to the relevant public procedure, concept, and persisted format.

## Rejected Zensical uses

Do not use these patterns during authoring:

- Sequential procedure steps placed in tabs.
- Requirements or corrective actions available only inside collapsed content or footnotes.
- Nested tabs or several nested collapsible blocks that conceal the reading order.
- Code annotations that merely restate YAML, TOML, JSON, or shell syntax.
- A diagram that repeats a short paragraph or table.
- A class diagram as a substitute for a supported-interface decision or grouped object prose.
- Icons or emoji on every page, heading, or admonition.
- Tooltips on every repeated term after its first useful definition.
- Tags used as the primary navigation structure.
- Primary-action buttons on deep reference pages.
- Global CSS that hides generated members, prevents ordinary wrapping, or compensates for an
  unverified template override.

These exclusions keep components tied to reader needs. A feature may be added later only after its
purpose and verification are recorded in the documentation-site specification.
